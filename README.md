# remnanode-ros

Неофициальная RouterOS-совместимая сборка [Remnawave Node](https://github.com/remnawave/node).

Образ собирается из последнего upstream-релиза Node. Ежедневный workflow
проверяет его новую версию и публикует новые образы `amd64` и `arm64` только
при выходе релиза. Xray-core и s6-overlay берутся из Dockerfile самого upstream Node.

При сборке workflow клонирует этот upstream-тег и подменяет в нём ровно один
файл — нативный бинарник `nftables-napi`. Зависимости Node не переопределяются,
`package.json` и lock-файл остаются нетронутыми. Сам финальный образ всегда
собирается оригинальным Dockerfile соответствующего Node-релиза, а не его копией
из этого репозитория.

## Совместимость с RouterOS

`nftables-napi` собирается из апстримного тега с наложением патча из
[patches/](./patches). Версия тега зафиксирована в
[NFTABLES_NAPI_VERSION](./NFTABLES_NAPI_VERSION); если релиз Node пинит другую
версию, сборка падает с явным сообщением, а не публикует образ с бинарником от
другого API. При доступном `CAP_NET_ADMIN` это позволяет использовать плагины,
которым требуются nftables:

- Ingress Filter;
- Egress Filter;
- Torrent Blocker;
- Connection Drop.

В финальный образ не добавляется `nft` CLI и не нужны дополнительные ENV для
совместимости.

### Что изменено в nftables-napi

Ядро RouterOS (на замерах — Linux 5.6.3) отвергает две необязательные
возможности set'ов, обе с `EINVAL`. Структура netlink-транзакции при этом
полностью апстримная: таблица по-прежнему создаётся одним batch'ем.

- **Первая ошибка batch'а вместо последней.** Batch — одна атомарная
  транзакция: как только set отвергнут, все ссылающиеся на него rules падают с
  `ENOENT`, и вызывающий получал следствие вместо причины. Из-за этого не могли
  сработать и обе повторные попытки ниже.
- **Ожидание первого netlink ACK.** `select()` с нулевым таймаутом мог вернуть
  «нет данных» до того, как ядро выложит ACK, и отвергнутый batch рапортовался
  как успешный. `EINTR` теперь ретраится, а не считается отказом.
- **Опция `counters` и лесенка повторов при `EINVAL`.** Счётчики — самое новое
  из того, что запрашивается: stateful counter-объекты и set-выражения
  (`NFT_SET_EXPR`, Linux ≥ 5.7). `createTable()` отдаёт минимум на каждом шаге —
  сначала per-element выражение, потом флаг `NFT_SET_CONCAT`, и только в
  последнюю очередь счётчики целиком. На RouterOS 5.6.3 лесенка
  останавливается на варианте «без per-element и без `NFT_SET_CONCAT`», то есть
  именованные счётчики заблокированного трафика сохраняются.
- **Повтор без `NFT_SET_CONCAT` при `EINVAL`** для concat-сета протокол+порт
  (`tcp . 443`); дескриптор concat при этом остаётся.
- Когда ступень сработала, в stderr уходит одна строка с тем, что именно было
  отдано, — молчаливая деградация возможностей оставила бы вопрос «куда делись
  счётчики» без ответа.

На ядрах, поддерживающих обе возможности, первая же попытка успешна и ни один
повтор не выполняется.

## Теги образа

- `latest` — последняя автоматическая сборка;
- `node-<node>-xray-<xray>` — точная комбинация upstream Node и Xray-core.

Образы для `amd64` и `arm64` публикуются в `ghcr.io/medium1992/remnanode-ros` и
`medium1992/remnanode-ros`. Версия Node последней сборки хранится в
[VERSIONS](./VERSIONS).

## Требования RouterOS

Нужны RouterOS с пакетом `container`, включённый `device-mode container=yes` и
доступный контейнеру `CAP_NET_ADMIN`. NFT-плагины поддерживаются на RouterOS
`amd64` и `arm64`; для остальных архитектур образ не публикуется. Используется
обычная конфигурация Remnawave Node — отдельный формат ENV или конфигов не
вводится.
